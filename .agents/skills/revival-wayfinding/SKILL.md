# Revival wayfinding

Use bounded investigation to turn real uncertainty into one supported project decision and the next observable contract. Wayfinding ends when implementation can proceed. It is not a second roadmap, issue hierarchy, specification system, or standing planning process.

## Trigger gate

Use this skill only when all of these are true:

1. the destination can be named as a concrete decision, contract, or amendment;
2. multiple dependent unknowns prevent that destination from being stated safely;
3. the accepted documents, current ledgers, pinned source, and local code do not already answer them;
4. the investigation can be bounded by evidence and a stopping condition.

Do not use wayfinding because a task is merely large, unfamiliar, or multi-file. Do not use it to postpone a known dependency island, implementation, test, or review. If one direct source trace or documentation lookup answers the question, perform that lookup and continue without starting a wayfinding effort.

These decisions are already made and are not wayfinding topics: Apple-native Swift and Metal, the one-way D3Import boundary, the complete resident Training `Level` baseline, one production path, the human-first creator suite, source-led semantic translation, and red-first production behavior. Reopening one requires the evidence and approval process in the owning accepted document.

## Canonical authority

Read [`AGENTS.md`](../../../AGENTS.md), the accepted document that owns the destination, the relevant source-translation ledger rows, and the current domain document.

Wayfinding working notes are temporary. They may live in the active task, a bounded research note, or an explicitly requested issue, but they never become a parallel source of truth. Do not create a wayfinding map, shadow roadmap, decision-ticket tree, duplicate backlog, or permanent status ledger.

As soon as a decision is supported and authorized, update its canonical owner:

- source mapping, disposition, baseline, or local deliberate difference goes in the source-translation ledger;
- a domain workflow or contract goes in its accepted domain document;
- a product, persistent semantic, or cross-workstream architecture change uses the binding amendment process;
- a repeated implementation failure updates the narrow owning skill or rule;
- test evidence stays with the test, commit, or pull request record that owns the change.

If approval is required, present one explicit proposed amendment and stop. Do not record it as accepted before the user approves it.

## Frame the investigation

State:

- the destination;
- the binding constraints that will not be reconsidered;
- verified facts and their evidence;
- inferences, clearly separated from facts;
- the smallest currently answerable unknowns;
- dependencies between those unknowns;
- the evidence that would resolve each one;
- the person or accepted document with decision authority;
- the condition that ends wayfinding.

Do not pre-slice unknown work into implementation tasks. Ask only questions whose answers can change the decision or remove a branch.

## Investigate the frontier

Start with the earliest unresolved question on which later questions depend.

Use evidence in this order where applicable:

1. accepted Revival documents and recorded amendments;
2. pinned released source, editor callers, revision evidence, and runnable reference behavior;
3. current ledger entries, canonical fixtures, local captures, and project code;
4. official Apple documentation and reproducible experiments;
5. measured optimized behavior on the recorded M4;
6. clearly labeled inference.

Historical source decides what the original did. Accepted documents decide what this product is building. An Apple API's availability proves neither a requirement nor an architecture.

Delegate independent research questions only when their evidence sets do not overlap. Give each investigator one bounded output and one owner. The root agent reads the binding documents, resolves conflicts, and keeps the canonical record coherent. Do not send multiple agents to produce competing full plans and average their opinions.

When a repeated source-to-Swift mapping is uncertain, take a representative case through the real product checkpoint before widening it. When the question itself is unknown, a disposable nonshipping spike may capture a format, timing trace, Metal behavior, or reference result. It creates no product interface and is deleted or archived as evidence before production implementation.

## Resolve one direction

For each resolved unknown, record:

- the answer;
- evidence and exact source location, command, capture, or measurement;
- the product consequence;
- remaining uncertainty;
- the canonical document or ledger location updated.

Remove branches disproved by evidence. Do not retain several possible architectures as modes, feature flags, or future-proof seams. Do not turn a provisional hypothesis into a default implementation.

If the evidence is insufficient, say what remains unproven and obtain the next bounded fact. When the bounded evidence sources named in the investigation are exhausted and no safe progress remains, report the named blocker rather than manufacturing a decision.

## End wayfinding

Wayfinding is complete when the team can state:

- one chosen direction within accepted authority, or one explicit amendment awaiting approval;
- the next observable player or creator contract;
- the source and ledger scope it touches;
- the first focused red test, unless the next action is still nonshipping research;
- which temporary notes or spikes were removed or archived.

Then stop wayfinding and hand the work to the relevant implementation skill. Shipping code still starts with the TDD protocol. Research output is not production progress.

## Valid and invalid uses

Valid examples include:

- an undocumented retail field whose meaning blocks canonical import;
- ambiguous source ordering that changes a reachable Training behavior;
- a Metal lifetime question that must be reproduced before ownership can be stated;
- measured M4 evidence that activates an accepted amendment gate.

Invalid examples include:

- choosing between resident loading and streaming before the recorded gate;
- redesigning the scheduler before flight, collision, and interval evidence exists;
- planning a generic ECS, job system, renderer abstraction, behavior VM, or asset database;
- deciding whether the editor or player should use a separate world path;
- creating tasks for roadmap work whose direction is already accepted.

## Output

Return only:

1. destination and fixed constraints;
2. resolved decisions with evidence and canonical locations;
3. remaining blockers or `none`;
4. next observable contract or proposed amendment;
5. temporary research disposition.
