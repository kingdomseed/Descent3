## How to use this ledger

Each row names one useful capability, its current historical evidence, the native owner and planned phase, and the proof needed to close it. Phase 0 must inspect the cited source, add missing evidence, and split any row that still hides independently testable behavior. A row closes only when every applicable runtime, authoring, validation, playtest, and publishing path works. `N/A` is allowed only with a recorded reason.

This ledger records capability state and completion proof. The active slice, lane and evidence boundary, and current developer ownership live in the [current implementation plan](current-plan.md); update that plan when execution state changes instead of adding a second task queue here. Update this ledger when evidence changes a capability row.

This is a capability ledger, not the file-transfer ledger. [Source translation discipline](source-translation.md) separately accounts for every relevant C++ file and symbol, including platform replacement, evidence-only, exclusion, and deliberate semantic differences. Neither ledger substitutes for the other.

Implementation evidence includes the focused red and green results required by [Test-driven development](test-driven-development.md). This does not mean one test per row, branch, or line. One focused test may protect a shared contract; independently failing contracts receive separate red-green slices. Every retained test must pass the test-value gate. A ledger row does not authorize speculative coverage of a path the product never runs.

States are `inventory`, `researched`, `specified`, `implemented`, `verified`, `replaced`, or `excluded`. `T-002` and `T-020` are verified for their exact Phase 1 import capabilities; that bounded evidence does not close any broader player, editor, presentation, behavior, or mobile capability. Owner aliases are `Import` for D3Import; `Core` and `Metal` for the required RevivalCore and RevivalMetal ownership boundaries; `Player` for a capability that must close through both concrete player shells, RevivalMac and RevivalMobile; `Mac` and `Mobile` only for platform-exclusive application boundaries; `Editor` for RevivalEditor; and `None` for an approved exclusion. `Player` is ledger shorthand, not a module, protocol, team, build target or generic platform abstraction. Shared Core and Metal behavior is proved once; the mobile integration state may remain open through Phase 7 without blocking a slice, phase, or Mac/shared row transition. Phase 8 closes accumulated mobile player composition on available physical devices; Phases 9 and 10 close their applicable mobile multiplayer and release obligations. Until then, a row may advance on its Mac/shared evidence while its mobile applicability remains explicitly unproven. An OS-inapplicable surface may be `N/A` only with a recorded reason and may not waive the underlying game capability. A public-service owner is named only if the accepted Internet-multiplayer research selects such a boundary.
